# Climber Demo 设计文档：拍照解抱石线路

- 日期：2026-10-26
- 状态：第 3 版（2026-10-27：M0 发现单张照片估不准真实距离，改为"墙面模型 + 照片对齐"，墙的几何与岩点分开处理，见 3.3、5.2、14 节）。第 2 版（2026-10-26）：先验证最大风险、加入墙角度和透视校正、兜底解单独标注、规则依赖可得数据、按里程碑拆分范围
- 范围：Web Demo（手机浏览器），用于验证主链路，并作为作品集项目

## 1. 目标与范围

### 1.1 一句话目标

用户在岩馆拍下一面抱石墙，点选一条线的颜色，系统识别出这条线的所有岩点；用户标出起点和 TOP 后，系统生成一套**运用技巧、省力优雅**的爬法，用 3D 胶囊人演示，并逐步讲解每个动作为什么这样做，帮助新手提升技巧。

### 1.2 本版包含（按里程碑交付，见第 14 节）

1. 拍照或上传照片，在本地缩到长边 1024 像素
2. 点选取色识别同色岩点，可调颜色容差，可手动增删点位
3. 标注起点手点（1～2 个）、起点脚点、TOP、只能踩脚的点；可选标注岩点类型和受力方向。这些是线路的事实，由用户确认，不交给模型猜
4. **墙面模型与照片对齐**（第 3 版）：每面墙有一个三维墙面模型（折面、各面角度、真实尺寸），照片对齐到模型后得到每个岩点的三维位置和所在面的角度；没有模型的墙用单张照片估算，并明确标为"可能不准"（见 5.2）
5. 输入身高（臂展可选，默认等于身高）；半透明人形对齐起点，只用于展示起始姿态，不负责定比例
6. 解法生成：可插拔大模型给出 2～3 个候选 → 规则校验 → 带违规原因重试 → 按优雅度排序；规则搜索兜底的结果单独标为"可行解（非推荐爬法）"
7. M1：在原照片上叠加手脚标记的**分步卡片**（只保留这条线的岩点颜色，其余变灰，同 M0 的 2D 预览）；M2：three.js 胶囊人动画（播放、暂停、逐步查看、拖动旋转视角）
8. 每一步的讲解：动作、技巧、为什么、新手常见错误
9. 路线数据存在本地（`localStorage`），可以导出和导入 JSON

### 1.3 本版不做（YAGNI）

账号体系、社区、云端存储、视频上传与姿态提取、全自动颜色聚类、物理仿真、训练专用模型、导入真实人物模型。

### 1.4 成功标准

- **M0**：在手写的线路数据上，至少有一个模型给出的爬法被用户（有经验的攀岩者）认可为"技巧型、省力"，并且能通过硬规则校验
- 在中端手机上，从拍照到出现分步卡片（M1）、动画（M2）的全流程可以走通
- 识别：合成测试图上点位数量和中心位置准确；真实照片经过少量手动修正即可用
- 解法：评测集上，硬规则通过率和优雅度可以量化，并能在不同模型之间对比
- 没有 API Key 时，整条链路也能用算法模式跑通

## 2. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | Next.js（App Router）+ TypeScript | 前后端在同一个仓库，`/api/solve` 和页面一起部署到 Vercel |

| 配置 | YAML（`yaml` 包） | 技巧词典和评分权重由用户手工调整，YAML 比 JSON 好写 |
| 测试 | Vitest、Playwright | 单元测试、集成测试、手机视口 E2E |

## 3. 架构

### 3.1 主链路

```
拍照 → 识别 → 用户确认线路（起步手脚、TOP、专踩脚点）→ 对齐到墙面模型（得到三维岩点）→ 身体参数
     → 解法生成（三维校验）→ 分步卡片（M1）/ 3D 动画（M2）+ 讲解 → 用户反馈（"这步够不着"）→ 重新规划
```

第 2 版的"透视校正 + 墙角度"一步被墙面模型替代。原因见 3.3。

### 3.3 墙面模型与几何服务（第 3 版）

**为什么改**：M0 用一张岩馆实拍照片（D 线）验证时，坐标是按"整面墙一个平面、猜一个比例"从照片换算的。墙由多个折面和大型块面组成，仰拍时上部被压缩，墙角度也只能估。几何一错，校验器的"通过"就没有意义：模型在错误的坐标里给出了合规但真人做不到的爬法，起步脚也放错了。

**核心思路**：墙的几何几年才变一次，岩点几周换一次。所以每面墙只建一次三维模型，之后每张照片只负责识别岩点、对齐到墙面模型。

| 层 | 内容 | 来源 |
|---|---|---|
| 墙面模型 `WallModel` | 折面（平面）、各面角度、真实尺寸、置信度 | ① 标准训练板的已知布局（Kilter、MoonBoard）② 一次性扫描：短视频多视图重建（VGGT 一类模型）或 LiDAR ③ 单张照片单目深度估算（Depth Anything 3 米制版、Depth Pro 一类），标为低置信度 |
| 线路 `Route` | 岩点、起步手脚、TOP、专踩脚点 | 照片识别加用户确认 |
| 三维岩点 `Hold3D` | 三维位置、所在面的法向和角度 | 照片对齐到墙面模型后，把岩点像素投到墙面上 |

**几何服务**：建模、对齐、深度估计需要 GPU，单独做成一个 Python 服务，网页后端通过固定接口调用。Demo 阶段跑在用户自己的电脑上（RTX 4070，12GB 显存），以后换成按次付费的云 GPU 只改服务地址。手机访问：同一个 Wi‑Fi 下用内网地址加文件上传；对外演示用 Cloudflare Tunnel 或 ngrok 提供 HTTPS。

**同一面墙的建模只做一次**：第一个用户拍一段短视频建模，之后所有用户在这面墙上只拍一张照片。

## 4. 识别（`lib/vision`）

1. 解码照片，把长边缩到 1024 像素，得到 `ImageData`
2. 用户点一下某个岩点，取点击处 5×5 区域的 HSV 中位数作为参考色
3. 掩膜条件：色相差 ≤ `hueTol`（默认 12°，可用滑块调），饱和度 ≥ `minSat`，亮度在 `[minVal, maxVal]` 之间
4. 形态学处理：先开运算（3×3）去掉噪点，再闭运算（5×5）填补镁粉造成的空洞
5. 连通区域标记（两遍扫描加并查集），过滤掉面积不在 `[minArea, maxArea]` 之间的区域（按图片面积比例设定）
6. 输出 `DetectedHold { id, cx, cy, bbox, areaPx, radiusPx }`；其他颜色的像素显示为灰色
7. 用户可以点击删除误识别的点，也可以长按空白处手动加点

## 5. 墙面几何、墙角度与身体模型（`features/calibrate`、`lib/geometry`、`lib/body`）

第 3 版起，`features/calibrate` 和 `lib/geometry` 改为对接几何服务（3.3）：墙面模型的选择或建模、照片对齐、三维岩点。3.2 目录结构里的"墙面四角、单应性矩阵"只保留为没有墙面模型时的手动兜底。

### 5.1 为什么不能直接用人形定比例

在地面上仰拍时，越高的点在照片里越被压扁。只在起点附近定一个比例尺，往上的距离会被系统性低估，TOP 附近的误差可能达到 20%～30%，跨度类规则会误判。

### 5.2 照片对齐到墙面模型（第 3 版，替代第 2 版的"四角透视校正"）

1. 有墙面模型时：估计这张照片的相机位置和朝向（和模型做特征匹配），把每个岩点的像素中心沿视线投到墙面模型上，得到三维位置和所在面
2. 标准训练板：板面就是一个已知角度的平面，岩点位置是固定布局，照片只用来识别"这条线点亮了哪些点"
3. 没有墙面模型时：用单目深度模型估出深度，拟合出各个折面，再用一个比例参照定尺寸（墙上螺母孔网格常见 6 或 8 英寸，即约 15～20cm，但各馆不同；或者用户输入一个已知长度）。结果标为低置信度，界面提示用户核对
4. 第 2 版的"点四角、按一个平面拉正"只适合单一平面的墙，保留为最后的手动兜底

### 5.3 墙角度

每个岩点使用**所在折面的角度**，不再整面墙一个角度。它会传给模型用来选择技巧，校验器的 R12（不陡的墙上挂脚要挂在侧面）也按每个点所在面判断。没有墙面模型时，由用户为整面墙选一个角度。负数表示正墙（slab），0 表示直墙，正数表示仰角。

### 5.4 身体模型

- 用户输入身高 H（必填）和臂展（可选，默认等于 H）
- 半透明人形只用于对齐和展示起始姿态，不参与定比例
- 身体尺寸推导（比例系数是命名常量，见 `lib/body/constants.ts`）：

| 推导值 | 公式 |
|---|---|
| 肩宽 | 0.23H |
| 单臂长 | (臂展 − 肩宽) / 2 |
| 肩高 | 0.82H |
| 腿长（髋到脚底） | 0.53H |

## 6. 数据结构（`lib/beta/types.ts`）

```ts
type Limb = 'LH' | 'RH' | 'LF' | 'RF'

interface Hold {
  id: number
  x: number; y: number; r: number            // 单位 cm
  role: 'start-hand' | 'start-foot' | 'top' | 'normal'
  type?: 'jug' | 'crimp' | 'sloper' | 'pinch' | 'pocket' | 'volume'
  pullDirDeg?: number                        // 受力方向：0° 往下拉，90° 侧拉，180° 反提
}

interface Body { heightCm: number; armSpanCm: number }

interface Wall { widthCm: number; heightCm: number; angleDeg: number }   // angleDeg：负数正墙，0 直墙，正数仰角

type Pose = Record<Limb, number | null>      // 点位 id；脚为 null 表示踩墙或悬空

type Grip = 'pull' | 'side-pull' | 'undercling' | 'gaston' | 'pinch' | 'push'
type FootTech = 'front' | 'inside-edge' | 'outside-edge' | 'heel-hook' | 'toe-hook' | 'smear' | 'flag'

interface BetaStep {
  limb: Limb
  to: number | null                          // 只有 smear 和 flag 可以是 null
  grip?: Grip                                // 手的步骤
  foot?: FootTech                            // 脚的步骤
  hips: 'square' | 'left-in' | 'right-in'
  hipsToWall: 'close' | 'normal' | 'far'
  motion: 'static' | 'deadpoint' | 'dyno'
  techniques: string[]                       // 对应 techniques.yaml 里的 id
  note: string                               // 这一步做什么
  why: string                                // 为什么这样做
  commonMistake?: string                     // 新手常见错误
}

interface Beta {
  label: string                              // 比如"技巧解""稳妥解"
  startPose: Pose
  steps: BetaStep[]
  source: 'model' | 'hybrid' | 'fallback' | 'user'
  recommended: boolean                       // fallback 恒为 false，不参与推荐排序
}
```

约束：每一步只移动一个肢体；`simulate(startPose, steps)` 生成 `Pose[]`，校验器和动画都消费它。

## 7. 解法生成

### 7.1 SolverProvider 接口

```ts
interface SolverInput {
  holds: Hold[]; body: Body; wall: Wall; startPose: Pose
  image?: { base64: string; mediaType: 'image/jpeg' }  // 只有模型支持看图时才发送
  techniques: TechniqueEntry[]
  candidates: number                         // 默认 3
}
interface SolverProvider {
  readonly id: string
  readonly supportsVision: boolean
  solve(input: SolverInput, history: ConversationTurn[]): Promise<SolverOutput>
}
interface SolverOutput {
  rawTurn: ConversationTurn                  // 原样保留，重试时追加到对话里
  betas: unknown                             // 由 schema.ts 用 Zod 解析
  usage: { inputTokens: number; outputTokens: number; estimatedUsd: number }
}
```

实现：

| Provider | 说明 |
|---|---|
| `AnthropicProvider` | 官方 SDK；默认模型 `claude-opus-5-5`，可通过配置换成 `claude-sonnet-5-5`、`claude-haiku-5-5`；用流式请求加 `finalMessage()`；自适应思考；开启服务端 `fallbacks: "default"`；重试时把 `response.content` 整块原样追加 |
| `OpenAICompatProvider` | 通过 `baseURL` 适配 DeepSeek 等兼容 OpenAI 接口的服务；`supportsVision` 按模型配置 |
| `MockProvider` | 从 `eval/` 或测试样例读取预设回复，零成本；可以按剧本返回合法、违规或格式错误的回复 |

配置（环境变量，只在服务端读取）：`SOLVER_PROVIDER`、`SOLVER_MODEL`、`SOLVER_BASE_URL`、`SOLVER_API_KEY`、`SOLVER_DAILY_LIMIT`。前端只能从 `config/models.yaml` 的白名单里选择模型 id，不能传入 URL 或 Key。

### 7.2 输入降级

一律发送文字版点位数据（编号、归一化坐标、半径、角色、类型、受力方向）。模型支持看图时，额外附上标了编号的照片，并要求模型补充判断岩点类型和受力方向。不支持看图的模型照样可以出解法。

### 7.3 编排流程（`orchestrate.ts`）

```
第 1 次调用（要求 N 个候选）
  → Zod 解析 → 每个候选 simulate + verify
  → 有候选通过硬规则？
       是 → 有质量提示（目前是 S5）且还有质量重试次数（默认 1）？
              是 → 把提示反馈给模型再改一次；改后更差或违反硬规则，就用之前通过的候选
              否 → 按优雅度排序，返回
       否 → 取违规最少的候选，把违规原因追加到对话里 → 重试（最多 MAX_RETRIES = 2）
  → 重试用完仍不通过
       → 从模型最后一个合法姿态开始 A* 搜索补完 → source: 'hybrid'
       → 补不上 → 从起点开始完整 A* 搜索 → source: 'fallback'
       → 仍然无解 → 返回无解，附带卡住的步骤和点位
```

**兜底解的定位**：A* 只搜"手脚落在哪个点"，产出的天然是"能爬上去"的解，不是技巧型爬法，和本产品"教漂亮爬法"的目标不一致。因此：

- `fallback` 和 `hybrid` 中由算法补出的步骤，在界面上明确标为**"可行解（非推荐爬法）"**，`recommended: false`，不参与"推荐"排序
- 算法步骤用简单规则自动补常见的技巧标记（下一个手点在侧上方且岩点受力朝侧面 → 标 `twist-lock`；脚点高于髋 → 提示 `rock-over`），讲解里注明"由算法推断，仅供参考"

接口：`POST /api/solve`，请求体为 `{ modelId, holds, body, wall, startPose, image? }`，返回 `{ betas: Beta[], attempts, usage, warnings }`。

### 7.4 成本控制

- 缓存：以 `hash(holds, body, wall, startPose, modelId)` 为键缓存结果，命中时不调用模型
- 每日调用上限 `SOLVER_DAILY_LIMIT`；超过后自动改用算法模式
- 每次调用记录 token 用量和估算费用，界面上显示本次费用
- 兜底步骤的讲解用本地模板生成，不额外调用模型

## 8. 校验器（`lib/beta/verify.ts`）

距离一律从岩点边缘算起（中心距离减去 r）。所有阈值都是命名常量。

### 8.1 硬规则（不通过会触发重试）

| 编号 | 规则 | 条件 |
|---|---|---|
| R1 | 引用合法 | 点位 id 都存在；起始姿态双手在起点手点上；结束时双手都在 TOP 上 |
| R2 | 双手跨度 | 两手距离 ≤ 臂展 × 0.95 |
| R3 | 手脚跨度 | 任意手到任意脚的距离 ≤ (肩高 + 单臂长) × 0.95 |
| R4 | 双脚跨度 | 两脚距离 ≤ 0.9H |
| R5 | 支撑 | 移动任何肢体时，剩下的肢体里至少有一只手在点上 |
| R6 | 脚不高过手 | 脚不高于两手平均高度 20cm 以上，除非是 `heel-hook` 或 `toe-hook`；挂脚跟、勾脚尖也不能比较高那只手再高出 40cm 以上（否则身体倒挂，M0 中 DeepSeek 曾利用这个豁免给出脚比手高 1.4 米的姿势） |
| R7 | 交叉 | 左手在右手右边超过 15cm（脚同理），而这一步没有标 `cross` |
| R8 | 防死循环 | 没有重复的姿态；总步数 ≤ 40 |
| R9 | 旗式平衡 | `flag` 的那只脚在重心另一侧，起平衡作用（代替 R5 对这只脚的要求） |
| R10 | 手脚不同点 | 脚不能踩在手正抓着的点上，反之亦然；techniques 含 `rock-over` 或 `mantle` 时除外 |

技巧带来的放宽：`hips` 是 `left-in` 或 `right-in` 时，髋贴墙一侧的手负责锁定，**对侧**手的 R2、R3 上限 × 1.1（例如左手侧拉、左髋贴墙，右手伸出去够得更远）；`motion` 是 `dyno` 或 `deadpoint` 时，R2、R3 上限 × 1.1。

**放宽的延续**：靠技巧达成的伸展或交叉，只要相关的两个肢体还在原来的点上，后续步骤继续允许，直到其中一个肢体移动。否则"定点抓到之后移动脚"这样合理的动作会被误判。

**原则**：硬规则只能依赖一定拿得到的数据（点位坐标、角色、身体参数、墙尺寸）。依赖可选标注的检查一律做成软规则。

### 8.2 软规则（只提示）

| 编号 | 规则 | 条件 |
|---|---|---|
| S1 | 无脚移动 | 移动手时两只脚都不在点上（campus） |
| S2 | 重心偏移 | 估算重心偏出支撑范围，有甩门风险 |
| S3 | 发力提示 | 动态或定点步骤，提示"需要发力" |
| S4 | 用力方向 | `side-pull`、`undercling`、`gaston` 的用力方向和岩点 `pullDirDeg` 偏差 > 60°；只有岩点标了受力方向才检查。手机照片里受力方向很难可靠判断，所以不作为硬规则 |
| S5 | 正墙侧身 | 墙角度 < 0° 时，有步骤用了侧身（`hips` 不是 `square`）或扭转、落膝、外侧踩；整套爬法只给一条提示并列出步骤 |

配合 S5，路线提示词按墙角度给出技巧方向：正墙以正身、踩墙、高脚和翻上为主；直墙正身侧身都常用；仰角（≥ 15°）多用挂脚、勾脚、扭转、落膝和顶胯。

### 8.3 违规原因格式

```ts
interface Violation {
  step: number; rule: string; limbs: Limb[]; holds: number[]
  actualCm?: number; limitCm?: number
}
```

渲染示例：第 4 步：右手移到 #12 后，左手（#7）和右手（#12）相距 196cm，超过最大双手跨度 162cm。第 1～3 步合法，请保留，从第 4 步开始重新规划。

每次最多发送 5 条，按步骤排序，并明确告诉模型哪些步骤是合法的、需要保留。

## 9. 优雅度评分（`lib/beta/score.ts`，权重在 `config/scoring.yaml`）

评分只用 `Pose[]`、`BetaStep[]` 和几何量计算，**不依赖 IK 或动画模块**，这样 M0、M1 阶段（还没有动画）也能评分。

| 维度 | 加分 | 扣分 | 几何近似 |
|---|---|---|---|
| 省力 | 手臂伸直挂着、髋贴墙（`hipsToWall: close`） | 长时间屈臂锁定、`far` | 屈臂：估算肩点（由双手、双脚和身体尺寸推算）到手的距离 < 0.6 × 单臂长，并持续 ≥ 2 步 |
| 用脚 | 先上脚再上手、脚点精准 | 无脚移动、频繁换脚 | 手的步骤之前有没有脚的步骤；S1 次数；同一只脚连续移动次数 |
| 技巧匹配 | 侧向受力的点配扭转；反提配高脚；圆包配低重心；仰角配挂脚、勾脚 | 侧向受力的点用正身硬拉 | 根据 `techniques.yaml` 里每个技巧的 `when` 条件，检查对应的几何特征和墙角度 |
| 流畅 | 步数少、重心轨迹平滑 | 来回换手、重复调整 | 总步数与"最少步数"之比；重心折返的次数 |

```yaml
# config/scoring.yaml（示例，用户维护）
weights:
  efficiency: 0.30
  footwork: 0.25
  techniqueFit: 0.30
  flow: 0.15
penalties:
  campusMove: 2.0
  bentArmHoldSteps: 0.5
  squareOnSidePull: 1.5
```

总分归一化到 0～100。界面默认展示得分最高的通过硬规则的候选，同时可以切换到"稳妥解"对比。

## 10. 技巧词典（`config/techniques.yaml`，用户维护）

```yaml
- id: twist-lock
  name: 扭转（侧身）
  when: 下一个手点在侧上方，或者当前手是侧拉
  body: 同侧髋转向墙，肩贴墙，另一只手伸出去
  mistake: 正对墙面硬拉，手臂很快就累
  verifierHints: { hips: [left-in, right-in] }
```

初版收录以下条目，触发条件由用户审核：扭转、落膝、旗式（内旗、外旗、后旗）、挂脚跟、勾脚尖、侧拉、反提、推撑（Gaston）、捏、并手、换脚、定点、动态、顶胯（贴墙）、高脚翻上（rock-over）、踩墙（smear）、撑上 TOP（mantle）。

词典同时用于：提示词里的技巧约束、校验器的放宽依据、讲解文案，以及以后的学习模块。

- 场景：墙是平面，按 `wallAngleDeg` 倾斜，岩点按墙面厘米坐标放置成小圆盘，用识别时的颜色

- 不支持 WebGL 时，降级为逐步显示的 2D 关键帧图

## 12. 错误处理

| 阶段 | 问题 | 处理 |
|---|---|---|
| 拍照 | 太大或解码失败（如 HEIC） | `createImageBitmap` 解码并缩小；失败时提示换图 |
| 识别 | 0 个点或超过 60 个点 | 显示容差滑块，并给拍摄建议 |
| 编辑 | 缺起点或 TOP | 禁用"生成解法"按钮，并说明缺什么 |
| 对齐 | 照片对不上墙面模型（匹配点太少、残差太大）；没有墙面模型时没填比例参照或墙角度 | 不能进入下一步，提示换个角度重拍或补充参照；手动兜底时四个角没点全、四边形自相交也在这里拦下 |
| 身体 | 没填身高 | 不能进入下一步 |
| 模型 | 超时（流式，总共 60 秒） | 算一次失败，进入重试 |
| 模型 | 429 或 5xx | SDK 自带重试 2 次，之后算一次失败 |
| 模型 | JSON 格式不对 | Zod 失败算一次失败，带格式错误原因重试 |
| 模型 | 拒答 | 服务端 fallback 换模型；仍然失败走兜底 |
| 模型 | 没有 Key 或超过额度 | 改用算法模式，界面顶部提示 |
| 兜底 | 无解 | 提示卡在第几步，高亮相关点位 |
| 动画 | 不支持 WebGL | 2D 关键帧图 |

隐私：照片不在服务端保存，只转发给所选的模型服务商。服务端日志只记录服务商、模型、token 用量、费用估算、尝试次数和违规规则编号。

## 14. 里程碑

原则：**先验证最不确定、最致命的假设**。识别和编辑器只是工程量，一定做得出来；模型能否给出技巧型爬法，才是这个产品成立的前提，所以放在最前面。

| 里程碑 | 内容 | 验证什么 | 出口条件 |
|---|---|---|---|
| **M0 验证** | 手写 2～3 条线路的 JSON（点位、起点、TOP、墙尺寸和角度、身体参数）；技巧词典初稿；提示词；Zod schema；校验器（R1～R9 和 S1、S3、S4）；脚本调用多个模型，输出对比报告 | 模型能否给出技巧型、省力的爬法；不同模型的质量和成本差异 | 用户认可至少一个模型的爬法；否则先调整提示词、词典或方案，再进入 M1 |
| **M1 主链路** | Next.js 脚手架；拍照 → 识别 → 用户确认线路 → 对齐到墙面模型（几何服务）→ 身体参数 → `/api/solve`（Provider、编排、重试、兜底，三维校验）→ 分步卡片 → "够不着"反馈 | 端到端可用；讲解有教学价值 | 手机上能用真实照片走通全流程；G0a 通过后才开始，几何部分按 G0b、G0c 的结果选方案 |
| M2 动画 | three.js 胶囊人、IK、播放器 | 展示效果 | 扭转、落膝、顶胯在动画里看得出来 |
| M3 质量 | 多候选、优雅度排序、评测集与对比脚本 | 量化效果，按数据调整 | 有一张各模型的对比表 |

M0 的代码放在 `spike/m0/`，其中的类型、提示词、校验器在 M1 迁移到 `lib/`。

### 14.1 M0 结论与第 3 版新增的验证（2026-10-27）

**M0 已验证**：在给定几何下，DeepSeek（deepseek-flash）一般在 1～2 次尝试内给出通过全部硬规则的爬法，每条线约 $0.02～0.06。实拍线路暴露并补上了一系列校验器漏洞：身体压缩（R11）、踩墙"瞬移"、挂脚绕规则（R12）、回复被截断和长连接断开。2D 动画预览（`npm run preview`）能直观看出这类问题。

**M0 未验证**：从照片得到可靠的几何。D 线的解法被用户判定为不正确，原因是从单张照片估出的距离不准，起步脚也放错了（应为左脚 #15、右脚 #14）。

**新增验证（在 M1 之前，不需要去岩馆）**：

| 验证 | 数据 | 验证什么 |
|---|---|---|
| **G0a：Kilter 解法验证（先做）** | Kilter Board 的固定布局和真实线路（通过 BoardLib 获取）。所有安装的岩点位置和朝向相同，角度 0°～70° 可调；线路标有起步、手点、TOP 和专踩脚点 | 几何精确时，爬法是否正确、是否省力；规则在不同角度下是否合理 |
| G0b：单目深度误差 | AscendMotion（12 面激光扫描的真实墙，附熟练攀岩者的三维动作，CC BY-NC-ND）；Sketchfab 上的岩壁扫描模型 | 从扫描渲染出虚拟照片，测单目深度模型的厘米级误差，决定"没有墙面模型时用单张照片估算"这条兜底是否够用 |
| G0c：对齐与建模 | 用户之后在岩馆拍的短视频和照片 | 短视频建模和单张照片对齐的精度 |

## 15. 待确认事项

1. 用户提到的技巧"顶息"具体是指哪个动作（目前按顶胯或定点理解）
2. 技巧词典初稿的触发条件，需要用户审核
3. 规则阈值（0.95、0.9H、20cm、15cm、60°、× 1.1）是根据常见人体比例设定的初始值，需要用户结合自己的实测数据校准
4. 评测集：先用现成数据（Kilter 线路、AscendMotion 扫描和动作）；用户之后在岩馆补充短视频、照片、几个实测长度和自己的爬法
5. M0 的样例线路先由 Claude 按典型抱石线路构造，用户用自己爬过的真实线路替换或补充
6. Kilter 数据来自其官方 App 的后端，作品集 Demo 使用前要看清使用条款，商用前必须确认授权；AscendMotion 是非商业许可
7. 部分重建、深度模型的权重只允许非商业使用，商用前要换成可商用的版本
